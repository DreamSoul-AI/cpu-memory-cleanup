# 六、候选研究方向
2026年10月27日讨论形成的候选方向：周期观察应用内存和系统压力，在桌面严重卡顿前尝试干预。该方向用于研究跨应用资源协调，尚未实现，不替换当前一键工作集整理，也不授权启动持续监测、限额、进程终止或权限操作。

## （一）问题、可行范围与系统能力
目标是保护用户当前任务的响应，评估是否能减少持续资源竞争。仅降低内存占用数字不构成成功。Windows 已提供进程内存统计、系统低内存通知和 Job Object 限额等能力，Agent 负责将用户优先级与这些能力结合，不能声称系统没有资源管理。[进程内存指标](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)、[压力通知](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification)

周期监测读取的是当前用量与增长趋势，不能知道程序未来全部需求，也不能发现哪些业务对象已无用。拦截每次申请属于另一层能力，不能由普通外部 Agent 的轮询实现。应用可能从已申请的内存池分配对象，外部系统统计不等于逐次业务申请记录。

| **观察范围** | **候选信号** | **限制** |
| --- | --- | --- |
| 系统 | 可用物理内存、提交余量、换页读入及磁盘响应 | 低内存通知只覆盖系统可用物理内存条件，需要其他信号补充，不能保证预测所有卡顿 |
| 应用 | 工作集、私有提交量、增长速度、进程身份与应用分组 | 共享页不能跨进程简单相加，多进程应用需要正确归组。权限不足保留未知 |
| 用户任务 | 前台活动、用户保护名单、可重跑任务与保存状态 | 前台不等于唯一重要任务，后台保存、会议和计算也可能需要保护 |

## （二）候选闭环与动作分级
```mermaid
flowchart TD
    OBS["周期采集与系统压力通知"] --> CHECK["检查持续压力、增长趋势与数据质量"]
    CHECK -->|无持续压力| OBS
    CHECK -->|需要处理| POLICY["按用户优先级及已授权能力选择对象"]
    POLICY --> ACT["建议或执行允许的最小干预"]
    ACT --> VERIFY["观察响应、压力与副作用，记录结果"]
    VERIFY --> COOL["恢复条件与冷却，避免反复动作"]
    COOL --> OBS
```

| **对象或阶段** | **可研究的干预** | **执行前提与代价** |
| --- | --- | --- |
| 通用观察阶段 | 提示压力来源，给出处理建议 | 无自动控制。不能仅凭高占用、低 CPU 或进程名称判断可关闭 |
| 有协作接口的应用 | 请求释放缓存、减少并发、停止接收新任务 | 逐应用核验接口、所有权、共享使用者、状态保存与完成确认 |
| 由 Agent 启动的受管任务 | 启动前设置预算，使用 Job Object 提交内存限额及通知 | 限额约束提交量，不等于物理 RAM 预留。硬上限可导致分配失败，需要应用处理，核验既有 Job、嵌套、子进程和权限 |
| 普通第三方应用 | 先提示，具备可靠接口时请求正常退出 | 无通用外部对象回收接口，不能随意修改堆或强制挂起 |
| 最后手段 | 评估明确授权下终止可重跑的受管任务 | 可能丢失状态，需另行修改并评审项目执行边界。本阶段不实现，不将按内存排名自动杀进程作为默认策略 |

Job Object 提供进程与任务组提交内存上限，另有只通知的阈值能力。硬限额交由系统执行，不能等同 Agent 每轮观察后的建议。[限额合同](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)、[通知合同](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_notification_limit_information_2)

## （三）AI 与执行器的职责
AI 适合解释趋势、梳理用户优先级和提出策略，轻量执行器落实身份、权限、规则、预算与记录。紧急判断不能依赖远程模型及时回复。采样周期、持续窗口和阈值先用合成轨迹校准，不预设通用内存百分比。动作后检查恢复并设置冷却，避免重复裁剪、误杀或规则振荡。

## （四）研究与验证顺序
1. 用合成轨迹验证持续增长、瞬时峰值、数据缺失、PID 复用、应用归组和多个压力来源，初版只输出建议
2. 另获授权后进行有界只读观测，记录监测自身开销、漏报、误报和用户任务响应，不接入真实清理
3. 优先在自有、可重跑的受管任务上比较无干预、规则干预和候选 AI 策略，分别验证预算、异常恢复与实际体验
4. 只有取得应用协作与效果证据后，再评审扩大自动动作范围。没有证据时保留建议模式

持续压力下的任务响应、误干预、动作次数及执行器自身成本共同评价，不能以可用量上升代替收益。内存瞬时暴涨、驱动故障、硬件异常和执行器自身失去调度仍可能造成卡顿，方案不承诺阻止所有死机。上述接口资料于2026年10月27日定向阅读，尚未实机验证。

## （一）目标与现状
目标是让桌面和网页都像一个轻量内存工具：打开看到清楚的内存状态，绿色按钮一次点击，处理时立即反馈，结果一眼可读，需要时再看细节。

桌面现状：desktop-memory-ui.cmd只负责定位仓库并启动pythonw及desktop-memory-ui.pyw，最终进入现有Tk主窗口；不是CMD负责绘制界面，也不是已打包独立EXE。主窗口已有约380×560的紧凑布局、圆环、实时显示、绿色按钮与折叠详情，但主窗口和workspace的控件风格不同，“查看详情”和“范围·方式·规则”两个入口也有职责重叠。网页已支持直接主按钮与实时显示，进程表和规则表单仍默认占据较大空间，并存在WEB-02圆环状态绑定问题。

继续使用现有Python标准库与Tk，不为美化换框架、增加桌面WebView或另造一套清理逻辑。两端共用视觉方向和业务口径，不要求浏览器与原生窗口逐像素相同。

## （二）共用界面与流程约定
| **区域或状态** | **网页与桌面共同目标** | **验收重点** |
| --- | --- | --- |
| 主区域 | 标题、内存圆环与读数、一个绿色工作集按钮、最近一次结果 | 层级清楚，主操作无需展开进程或设置 |
| 视觉 | 浅底、绿色强调、统一字号层级、稳定留白和对齐；按钮有正常、悬停、按下、禁用状态 | 桌面不再混用明显不同的主次控件风格，文字不拥挤或截断 |
| 就绪 | 显示当前内存与更新状态，绿色主按钮明确可用 | 实时值、暂停值和未知值可区分，不能把旧值当实时值 |
| 整理中 | 主按钮立即显示“正在整理…”，阻止重复派发，内存显示继续更新 | 不弹主动作二次确认，不跳页，不伪造原生百分比进度 |
| 完成 | 主按钮附近呈现时间、范围、前后变化和明确结果 | 读数继续变化不覆盖本次固定结果；变化方向准确，不称为保证提速 |
| 失败 | 同一区域展示未派发/已调用的事实及简短原因，细节可展开 | 错误不能只藏在原始JSON或弹出一串异常 |
| 更多内容 | 进程选择、保护、规则、方法和原始报告按需查看 | 默认关闭的规则不会因展开/折叠或换界面而被启用 |

默认工作集主按钮单击即执行的业务语义在两端一致；高级系统动作、定向批次、启用规则仍确认范围。实时只读显示和自动整理规则分开，不新增热键、托盘、开机启动、更多清理区域或性能实验。

## （三）具体开发任务
### POLISH-01 修正并统一可见状态
先修网页WEB-02：将占用角度和处理中状态作用到实际圆环；同时核对桌面数字、圆环与按钮状态映射，保留已正确的实时刷新逻辑，不为统一视觉重写Package。

验收：合成25%和75%读数下，数字、圆环及横条含义一致；清理中继续显示、减少动画设置或暂停行为有效；一次点击最多派发一次维护。网页缺陷修复不代表桌面天然通过，分别保留证据。

### POLISH-02 主界面紧凑与桌面视觉整理
网页默认收起空进程表与规则表单；桌面重新整理主窗字号、内边距、圆环比例、按钮尺寸与结果区，保持一个绿色主动作。以现有380×560附近尺寸为设计起点，按实际内容和缩放调整，不把固定像素尺寸作为硬约束。必要的提交量、路径和技术说明移至详情。

验收：两端主界面都能直接完成查看→整理→读结果；桌面标准缩放及150%显示配置下主按钮与结果不被截断，键盘焦点顺序合理，窗口不闪跳或因状态文案变化反复改变尺寸。缩放检查使用受控环境或进程内设置，不修改系统全局显示。

### POLISH-03 最近结果清楚且位置稳定
两端在主操作附近统一展示完成时间、动作范围、前后值与带方向变化；实时概览和上次结果各自标明。耗时依据实际记录的处理区间显示，未知不推测，不把快照时间差冒充原生API独占耗时。原始记录及完整错误继续放在详情。

验收：成功、部分结果与未派发均无需展开JSON即可理解；实时刷新不清空或改写最近结果，离线回看零维护；不为结果卡额外调用清理。

### DESKTOP-01 整合桌面详情与设置入口
核对现有“查看详情”和“范围·方式·规则”的职责，归并为清楚的一个详情入口，内部按“进程范围、整理设置、运行详情”分区；可使用现有次级窗口或折叠区，不新造窗口体系。统一Tk与ttk的字体、色彩和按钮层级，避免重复展示单进程和批次选择入口。

验收：选中对象、保护、方法及规则状态各有明确位置；打开次级内容不会重复打开多个工作区或意外读取进程，关闭次级内容不退出主窗、不改变已授权任务；主窗退出仍按原Package流程收尾。托盘及原生通知不在此任务内。

### DESKTOP-02 CMD启动与一致交付
保留现有CMD→pythonw→桌面入口，核对优化后仍能直接打开正确主窗，正常运行没有常驻终端。入口和产品模块继续分工，不把界面代码放进CMD或复制一份清理脚本；维护现有参数转发和启动失败提示。

验收：脚本受控测试验证入口分派不自动清理，正常启动路径指向同一Package；实际无常驻终端与原生视觉效果在明确允许的窗口验收中单列。仅有假控件测试不能宣称已完成真实Tk视觉验收，HTML预览也不能代替本地窗口证据。

## （四）实施顺序与验收
1. 先固定两端主界面布局及状态表，再完成POLISH-01实际绑定修复。
