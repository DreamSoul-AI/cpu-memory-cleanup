# 六、下一轮建议：跨平台能力与验证路径

状态：已启动Linux只读里程碑，不改动已发布的 Windows 默认策略。目标是复用现有 Package、CLI 与网页，按操作系统提供有证据支持的能力，不要求每个平台复制同一种清理动作或百分比效果。

## （一）CP-01 先回答各平台能做什么

优先核对 Linux 和 macOS 的真实容量、进程发现、压力信号及主动整理接口，整理能力矩阵，记录接口来源、权限、影响范围和限制。macOS 的压缩、缓存及压力指标不能直接等同 Windows 工作集裁剪，Linux 回收建议也不能等同删除内存。没有查明等价接口前不承诺全局“一键清理”。

产出进入现有通用调研，给出每个平台“已证实可做、候选待验证、不可用或不适用”。验收是能解释所选能力如何工作及如何检验，不是只列 API 名称。跨平台范围确定后再更新架构和代码结构设计，不提前新增空平台目录。

## （二）CP-02 没有 Mac，先准备可运行的验证环境

Linux 优先考虑可控虚拟机进行读取、服务启动及后续受控负载验证。WSL可用于部分开发检查，但不能据此证明独立Linux桌面与整机清理效果。

macOS 可评估 GitHub 托管 macOS runner，先完成原生编译、合同测试、真实只读与服务启动检查，分别登记实际测试架构。当前仓库未配置 Actions，本节只是拟议验证路径，不启用工作流、不租用机器，也不承诺免费额度或运行权限。需要租用云Mac时另确认预算及访问方式。

云端runner能证明对应环境中的运行，不能代替普通Mac用户负载、权限、浏览器体验、签名和分发提示的真机验收。后者留待借用Mac或有Mac的同事按明确清单协助，不必为开始调研立即购买设备。

## （三）CP-03 先交付可验收的跨平台基础版本

建议先 Linux、后 macOS。复用业务层、CLI和网页，平台差异收在系统接入和启动打包中，界面根据真实能力显示可用操作。首个里程碑是正式数据读取、目标发现、服务启停和报告格式一致。暂不支持整理的平台明确说明，不保留可以点击却无实际作用的清理按钮，不用动效冒充系统能力。

验收分别登记编译通过、真实读取、进程身份与资源释放、HTTP入口、打包启动及尚未验证项。Windows既有合同回归保持通过。只读基础里程碑不称为“跨平台清理已完成”。

## （四）CP-04 主动整理按平台单独证明

只有CP-01确认可行且环境具备后，才实现必要的系统适配。先对自有测试负载核对真实驻留变化、内容完整性、调用耗时和后续访问代价，再判断是否扩大范围，不在共享CI主机上默认整理其他进程。操作前明确授权及预算。

若 macOS 缺少合适的跨应用整理途径，可将其版本定位为真实状态和压力观察，或采用经验证的受限能力，不为按钮一致性引入高权限私有接口。是否需要该产品范围由调研结果决定，不预设苹果系统“不能清理”或一定存在Windows等价接口。

## （五）CP-05 按实际能力发布

逐平台提供匹配架构的启动入口和包，核对系统版本、运行依赖、权限、记录位置与停止方式。每个平台用解压后的真实产物验收，再在README和Release标注支持级别。未经过目标平台验证的包不标为正式支持，下载与签名体验待实际Mac环境核对后决定。

下一轮先完成CP-01与CP-02，再选择CP-03的最小交付范围，不一次性承诺三个系统功能完全一致。Windows v0.4.0继续可用；本轮候选实施不代表新增发布。

# 七、下一轮建议：小应用、Agent使用与跨平台

## （一）先明确本轮想得到什么

已有网页、Rust库和CLI均继续复用。下一轮让普通用户“安装后点图标就能用”，也让Codex能够通过现有工具完成实际任务。跨平台先确定可行能力和验证环境，不把换一个界面外壳当成已经支持macOS/Linux。

## （二）APP：从CMD入口变成可安装小应用

### APP-01 安装后直接点图标使用

候选交付为Windows当前用户安装包，创建开始菜单入口，可选桌面快捷方式，点击后启动或复用同一版本的本地后端并打开现有界面。不只是建立一个localhost网址快捷方式，因为服务关闭时网址本身不能启动程序。

先确定安装位置、日志/报告位置、升级与卸载方式，数据不依赖仓库target目录。默认不添加开机自启，不自动清理，不要求用户安装开发工具。保留便携ZIP供已有用户选择。

验收旅程：普通用户安装 → 点图标 → 看到真实读数 → 明确点击整理 → 看到真实结果 → 退出 → 重新打开。卸载后程序入口移除，运行记录保留与清理选项需说明。安装、升级和签名状态以实际产物记录，不把打包成功说成可正常安装。

### APP-02 评估独立小窗口与快捷按钮

用户希望的是像小应用一样方便调用。先比较“安装器加现有浏览器工作台”与“系统WebView独立窗口”两种体验。若独立窗口确实更合适，Tauri作为候选，复用现有网页和Rust Application，不复制清理代码，也不默认恢复Tk或重写一套界面。

先做最小窗口原型，核对窗口打开、重复点击复用、后台任务期间界面响应以及退出时任务收尾。选定方案后先改架构和代码结构设计，再接正式功能。托盘/菜单栏小按钮列为后续可选项：点击优先打开小窗口或工作台，不把“打开应用”隐式变成全局清理。是否需要悬浮按钮待原型试用后再定。

安装器不依赖必须先引入WebView框架。WebView有各平台运行时差异，不能只凭Rust核心能编译就承诺相同显示和分发体验。

## （三）AGENT：让Codex实际调用工具完成任务

### AGENT-01 先验证已有CLI是否真的好用

当前六个工具已存在，没有必要先新增另一套清理接口。安排一次Codex作为调用方的端到端测试：读取--tool-info，查询真实内存，发现目标，选择本次创建的自有测试进程，按明确授权整理一次，再用memory_result回看并解释结果。

测试不只记录退出码，还保留用户任务、工具选择、实际参数数组、JSON返回、Codex最终解释及原始Run。检查是否真的调用、是否选对进程身份、是否把动画或可用量净差误说成独占释放量/提速，以及partial时是否如实说明而没有自动重试或扩大范围。普通隔离测试继续保护系统，真实动作另有明确范围。

先以只读任务验证接入和描述，再安排自有负载动作，不在当前计划编写期间执行清理，也不先拿其他应用试错。结合结果修正工具描述和接入文档，而不只补更多参数。

### AGENT-02 验证网页和工具是否共用同一能力

针对同一版本的产物，分别让Codex用CLI和Computer Use在内置浏览器完成对应旅程，核对数据单位、范围、结果状态和记录协议一致。涉及真实维护时用分开的、恢复过的自有负载，不让两种入口并发清理，也不为了对齐数字强行改报告。

网页用来验收按钮、响应、结果和动效，CLI用来验收结构化调用。两者各有证据，不用网页点通代替Agent接入通过，也不用函数测试代替真实界面旅程。

### AGENT-03 有接入需要时再增加MCP适配

如果实际Codex使用验证表明，标准工具发现与宿主配置比直接CLI更方便，再评估本地stdio MCP适配。该适配只把现有六能力映射成工具，不新增另一份清理实现，结果与授权边界沿用现有合同。当前--tool-info是自定义静态目录，不把它称为已经实现MCP。

这一项是条件建议，先取得CLI任务测试结果再决定。未启动本项前不改Codex用户配置、不安装新服务、不向其他项目批量部署工具。

## （四）CP：沿用第六章，区分平台能力和应用外壳

CP-01先调查Linux/macOS的真实内存读取、进程发现及可行整理机制。Linux可先用可控虚拟机，macOS先评估托管runner的编译、只读及服务检查，普通Mac上的界面、权限和分发体验仍需要实际机器。没有等价清理能力的平台可以先提供明确标注的只读版本，不做只有动效的“一键清理”。

除了后端接口，还需调查系统随机源、默认浏览器打开、启动路径、数据目录和打包。当前非Windows装配为Unsupported，Unix随机源已有实现但目标环境运行仍需验证，不能只增加内存读取就宣布跨平台服务贯通。框架支持某平台不表示本应用系统功能已经支持该平台。
