**CPU 内存清理 代码结构设计**
更新日期：2026年10月21日。英文名称：Code Structure Design。状态：目标结构，尚未实施。设计依据为 [CPU 内存清理 架构设计](<CPU 内存清理 架构设计.md>)，技术机制与现状证据见 [CPU 内存清理 通用调研](<CPU 内存清理 通用调研.md>)。

# 一、范围与目录原则
本文确定代码放在哪里、每个 Python 文件承担什么职责、文件之间如何依赖，以及对应测试的位置。架构设计负责质量目标、运行合同、状态与部署，本文集中维护具体目录树和文件职责。

采用仓库根目录下的单个 `cpu_memory_cleanup` 包，保留 `python -m cpu_memory_cleanup` 启动方式。四项业务职责为交互、用例、分析规则和 Windows 接入，另设包入口及共享合同文件。产品模块与测试文件使用英文小写与下划线，启动脚本沿用既有或架构指定名称。

按实际职责落位，先使用单层包。只有同一文件内出现需要独立修改、独立验证的稳定职责时才拆成子包，并同步测试镜像。文件数量不是永久上限，不按旧文件逐一改名或搬迁。

# 三、Python 文件职责
## （一）包入口与装配
| **文件** | **主要内容** | **边界** |
| --- | --- | --- |
| `__init__.py` | 包说明及实际需要的版本元信息 | 导入时不启动流程，不聚合导入 GUI、Windows 接入或全部公共函数 |
| `__main__.py` | 受启动保护的 `main(argv=None)`，选择 CLI 或桌面入口，创建并连接用例与接入对象 | 装配代码不处理指标、执行维护或判断最终结果，不在模块导入时启动程序 |

装配创建的用例对象在一次 CLI 运行或一个桌面实例中共享。Windows 接入对象的创建不打开查询、互斥或权限作用域，原生资源在用例明确打开会话后取得。离线回看不打开 Windows 会话。Tk 仅在选择桌面入口时加载。
## （二）共享合同 contracts.py
| **内容** | **放在本文件中的定义** |
| --- | --- |
| `Sample` | 样本身份、时刻、原始指标、单位、CPU 覆盖及缺失原因 |
| `ActionRequest` | 用户确认的单一维护机制、实际范围和确认来源 |
| `RunReport` | 观察、解释、调用事实、恢复与记录状态、整体完成度 |
| `Reader` / `Maintainer` | 读取和单次维护需要的最小接口及资源责任，行为语义沿用架构设计 |

使用小型数据类或明确字段定义。与持久化版本有关的共享常量放在这里，序列化、文件读取和规则执行分别留在其使用方。模块不导入其它产品模块，不包含 Windows 句柄、DLL 类型、UI 控件或业务编排。
## （三）用例 core.py
本文件提供 `inspect`、`review`、`maintain` 三个用例入口，由同一个用例实例持有运行上下文。实现内部的辅助函数使用私有名称，调用方不直接调用记录函数或阶段转换。

| **文件内职责** | **具体内容** |
| --- | --- |
| 观察 `inspect` | 打开 Reader 会话、有界采样、调用规则、按请求记录、关闭资源并返回报告 |
| 回看 `review` | 校验并读取已保存运行，保留原条件，执行明确要求的比较或新版重算 |
| 维护 `maintain` | 检查确认和范围、协调会话、保存意图、至多一次派发、必要后观测与收尾 |
| 运行状态 | 运行 ID、活动流程、取消接受、派发边界与整体完成度，状态转换以架构设计为准 |
| 记录读写 | 运行目录、JSONL 格式检查、运行头、样本、动作事实和终态，保存失败保留真实调用事实 |

记录读写先作为本文件的私有函数。诊断使用标准库 `logging`，运行目录由调用参数提供，不新增独立存储框架。用例不创建窗口，不加载 DLL，不通过全局可变对象保存当前运行。
## （四）规则 rules.py
| **函数分组** | **处理内容** |
| --- | --- |
| CPU 分析 | 稳定进程身份、累计时间差、间隔、单核或全机口径、处理器组与覆盖缺口 |
| 内存分析 | 提交、工作集、Standby、可用量、缺页与 I/O 的解释及缺失处理 |
| 进程树与窗口汇总 | 按已提供身份和样本关系聚合，保留重复、缺拍与范围不一致 |
| `analyze` / `compare` | 产生解释和对照结论，分开数值变化、证据完整度及收益判断 |

各组先使用同一文件内的普通函数。输入为已校验的数据和显式条件，输出为分析结果，不在这里读取文件、查询系统、读取真实时钟或自动生成维护确认。CPU 与内存规则都通过同一用例入口使用。
## （五）Windows 接入 windows.py
| **文件内分组** | **处理内容** |
| --- | --- |
| 原生定义 | `ctypes` 结构、ABI、状态码和 DLL 绑定，在打开相关会话时取得实际能力 |
| 只读接入 | 主机、进程、CPU 与内存数据读取，PDH 查询及缺失原因，统一转换成合同数据 |
| 单项维护 | 单机制范围检查、互斥、只读预检、临时特权、至多一次原生调用及恢复 |
| 资源收尾 | 查询、句柄和互斥释放，分别返回调用、恢复和关闭事实 |

原生辅助对象和函数留在本文件内部。共享合同中的 `Reader` 与 `Maintainer` 可以由同一具体接入提供，读取调用方只使用读取能力。原生句柄不传给核心或界面。缺权限、不支持和未知分别报告，不自动提升权限或改换机制。
## （六）命令行 cli.py 与桌面 desktop.py
| **文件** | **主要内容** | **状态归属** |
| --- | --- | --- |
| `cli.py` | 参数解析、输入转换、调用用例、中文或 JSON 呈现、退出码映射 | 同步使用共享用例，最终状态和动作事实来自 `RunReport` |
| `desktop.py` | Tk 控件、明确选择、工作线程创建、结果投递、主线程 `after` 更新与窗口关闭 | 拥有控件和展示缓存，业务活动状态、取消是否生效及是否可接单由核心决定 |

GUI 工作线程执行同一用例，完成后将结果交回主线程，不从工作线程更新 Tk 控件。取消信号交给核心判定，线程结束或按钮变灰不能代替业务终态。两个入口都不导入具体 Windows 接入，不重新计算成功或加速结论。

# 四、文件间依赖约定
架构设计中的源码依赖图为关系依据，具体允许方向如下。源码依赖包含导入和类型引用，不表示运行时只能沿图单向返回数据。

| **文件** | **允许依赖的项目文件** | **限制** |
| --- | --- | --- |
| `__init__.py` | 原则上无 | 只保留必要包元信息 |
| `__main__.py` | `cli`、按需 `desktop`、`core`、`windows` | 只负责装配和入口选择 |
| `contracts.py` | 无 | 只依赖必要标准库 |
| `rules.py` | `contracts` | 无真实系统或文件副作用 |
| `core.py` | `contracts`、`rules` | 通过注入合同调用接入，不导入 `windows` 或 UI |
| `windows.py` | `contracts` | 不反向依赖核心、规则或 UI |
| `cli.py` / `desktop.py` | `core`，需要类型引用时使用 `contracts` | 不互相调用，不加载具体接入 |

跨文件复用只引用其公开入口。仅一个文件使用的小函数保留为该文件的私有函数。共享合同不引入流程，辅助代码不集中进没有明确责任的 `utils.py`。当前业务也不需要单独的 `worker.py`、服务容器或插件目录。

# 五、测试文件如何分布
## （一）源码镜像与测试内容
测试复制有效源码目录层级，`unit`、`integration`、`e2e` 作为标签。每个文件内的测试仍按单一信号划分，测试方法和元数据共同说明实际层级与路径。

| **目标代码** | **测试位置，位于 tests/ 下** | **主要验证内容** |
| --- | --- | --- |
| `cpu_memory_cleanup/__init__.py` | `cpu_memory_cleanup/test_package.py` | 导入不启动 GUI、采样或维护，必要元信息可读取 |
| `cpu_memory_cleanup/__main__.py` | `cpu_memory_cleanup/test_main.py` | 默认入口、装配与退出，选择离线模式不打开系统会话 |
| `cpu_memory_cleanup/contracts.py` | `cpu_memory_cleanup/test_contracts.py` | 数据边界、缺失语义、版本和最小合同 |
| `cpu_memory_cleanup/core.py` | `cpu_memory_cleanup/test_core.py` | 只读、维护、回看路径，取消、互斥、权限及保存失败，未知不重放 |
| `cpu_memory_cleanup/rules.py` | `cpu_memory_cleanup/test_rules.py` | CPU 与内存口径、合成窗口、进程树及收益证据 |
| `cpu_memory_cleanup/windows.py` | `cpu_memory_cleanup/test_windows.py` | 假 DLL 和合同，ABI 映射、原始状态、特权恢复和句柄关闭 |
| `cpu_memory_cleanup/cli.py` | `cpu_memory_cleanup/test_cli.py` | 参数到结果，默认零动作、中文路径、输出及退出码 |
| `cpu_memory_cleanup/desktop.py` | `cpu_memory_cleanup/test_desktop.py` | 主线程投递、重复点击、关闭取消及控件销毁后的结果处理 |
| `scripts/desktop-memory-ui.cmd` | `scripts/test_desktop_memory_ui.py` | 桌面启动目标、参数及退出码转发 |
| `scripts/desktop-memory-button.cmd` | `scripts/test_desktop_memory_button.py` | 既有按钮参数兼容，默认行为不被静默替换 |
| `scripts/tree-series.ps1` | `scripts/test_tree_series.py` | 采样参数转发，业务执行经过用例 |
| `scripts/run-tests.py` | `scripts/test_run_tests.py` | 清单选择、导入范围、逐项结果保存、失败和缺结果的退出行为 |

跨模块路径测试放在其入口对应的测试文件。只有一条旅程已需要单独维护时才在同一镜像位置增加场景文件。测试包标识文件不为自身生成递归测试，排除项记在 `tests/README.md`。
## （二）测试导入与执行入口
保留 `unittest`。统一入口以仓库根作为顶层导入目录，测试模块使用 `tests.cpu_memory_cleanup.test_core` 等完整名称。`tests/` 和其镜像子目录保留 `__init__.py`，不能把 `tests/` 作为顶层产品包搜索路径，否则同名镜像目录可能遮蔽 `cpu_memory_cleanup`。

`scripts/run-tests.py` 从自身位置定位仓库根，读取唯一 `tests/manifest.json`，先完成选择及条件检查，再按完整名称加载所选用例。需要目录发现时，以仓库根作为 `top_level_dir`，不先全量导入再筛选。测试模块导入时也不得创建 GUI、采样或维护，平台能力在所选用例执行时按需取得。离线计划只选择假接入及离线用例。五维元数据、预算、结果字段和放行条件沿用架构设计第六章，不在本文重复定义。

假 Reader、Maintainer 与合成数据先保留在使用它们的测试文件。多个文件已实际复用时再提取到 `tests/_helpers/` 或 `tests/_data/`，与产品镜像分开。测试辅助函数不以 `test_` 命名。真实 GUI、ABI 和平台实验仍需按明确计划验证，假路径通过不代表真实平台已通过。

# 六、源码、脚本与运行产物的界限
| **位置或文件** | **归属** | **规则** |
| --- | --- | --- |
| `cpu_memory_cleanup/` | 产品源码 | 包含运行逻辑和明确的模块边界 |
| `scripts/` | 启动兼容与研发入口 | 业务转发到包，测试入口只承担测试职责 |
| `tests/` | 测试代码、最小数据和测试计划 | 不进入产品运行依赖 |
| `docs/` | 三类维护文档 | 调研保存证据，架构保存行为约束，本文保存文件落位 |
| `samples.jsonl`、`operation.jsonl` | 实际运行目录中的业务数据 | 输出位置显式给定，不写入源码目录，不重建历史 `logs/` |
| 测试运行的 `manifest.json`、`events.jsonl`、`report.md` | 明确指定的独立测试结果目录 | 与 `tests/manifest.json` 的计划定义区分，不冒充源码或历史样本 |

当前运行依赖保持标准库，无需为目录设计增加依赖文件或打包体系。需要交付安装包时，再按实际产物定义构建配置与对应验证。缓存、虚拟环境和生成产物不复制进测试镜像。

# 七、落位与维护检查
1. 按架构设计的用户旅程增量实现，同步创建对应代码和有效测试
2. 对照本文检查文件责任与允许依赖，再按架构设计验证接口行为、状态与故障路径
3. 对既有命令、脚本及保存格式逐项决定兼容方式，记录参数和测试标识变化，不静默改变默认行为
4. 完成实际替代及兼容检查后再删除旧实现，更新测试清单、README 和本文
5. 拆分文件或新增子包时，同步源码与测试镜像、架构依赖关系和受影响调用方
