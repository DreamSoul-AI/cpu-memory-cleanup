# 一、确认的实现差异
app.js 的 run 开始调用 stop，解除显示动效后继续由 memory→paintMemory→MemoryDisplay.update 驱动主圆环。业务结束 present 又接收报告样本，然后 start 从当前显示位置下降。由此，整理期间真实读数变化与之后的装饰下降会先后出现在同一圆环，属于源码可确认的职责问题。

memory-display.js 在零位刷新回调返回后保存target，300毫秒回弹期间update仅改actual，终点后才重新追actual。因此出现先弹至某个旧目标、随后继续下降是当前设计允许的行为。35%与26%的确切来源尚无本次浏览器时间线，不能仅凭反馈判断为丢失数据或未执行清理。

用户试用已有Run 36e81ec574a8c36a0174cca811059b12：538个枚举，488成功、48跳过、2失败，原始partial；快照可用量16,177,168,384→27,718,299,648 bytes，总量50,586,136,576 bytes。这不是本轮Agent新执行，也不能用该Run唯一对应用户描述的35%或26%时刻。

# 二、360静态校准
重新校验原EXE与DLL的SHA256，仍与既有副本一致。复读360-animation-20261102中的窗口更新与定时器汇编。0xd9900检查下降标志后，0xd990f保存目标，0xd9922设置定时器2，0xdd27b回弹检查目标。该局部分支没有直接检查回弹标志来证明更新只能一次，周边0x1c8字段的完整门控仍须追清。

此前“回弹沿保存目标推进”仅说明定时器使用目标字段，不能扩大为所有更新回调在回弹期间都不能重设该字段。当前项目的固定目标后再追实时是一项设计选择，不是已证明精确复刻360。参见 [原静态追踪](<2026-11-02 360归零与回弹静态追踪.md>)。没有运行360或恢复其原始C++源码。
