记录日期：2026年11月3日。来源项目：CPU 内存清理。以下是Codex在本项目中实际采用的方法，先收集，不作为共用规范。

# 一、先把用户要的行为重新说清楚
项目最初要参考360的一键内存整理体验，开发中却偏向了诊断分析。Codex根据用户反馈重新确认“看真实读数、点一次按钮、执行一次整理、看真实结果”的主流程，再调整开发计划、架构与代码结构。

这里留下的经验是：出现反复返工时，先检查是否理解错了产品行为，而不是继续往现有页面里加信息。文件结构完整，不代表产品方向已经对齐。

# 二、用内置浏览器和Computer Use核对真实体验
之前代码检查和页面演示能够通过，但用户仍反馈卡顿、下降混合、回弹目标不对。Codex后来通过Computer Use在内置浏览器打开正式localhost网页，实际点击绿色按钮，查看开始反馈、真实容量更新、结果出现、归零及回弹的完整过程。这样无需占用用户桌面的鼠标键盘，也能检查网页本身的行为。

只看静态截图看不到阶段先后，因此同时保存页面截图、阶段与样本时间线、控制台错误，以及本次后端真实运行报告。把“后台什么时候完成”“页面什么时候显示结果”“圆环什么时候开始和结束”放在一起核对，才发现真实读数与装饰动效曾争用同一个显示状态。

```mermaid
flowchart LR
    A[发现问题] --> B[修改计划与实现] --> C[内置浏览器实际操作] --> D[核对真实结果]
```

真实清理是在明确授权后执行，普通回归使用隔离实现，避免自动操作主机。内置浏览器也曾因访问审核超时而无法验收，当时保留未完成状态，权限恢复后再继续，没有把离线测试写成实机通过。

# 三、解包360校准方法，再回到自己的实现验证
仅凭“360感觉更快”的描述，很难判断差别来自清理机制还是交互。Codex对固定版本的软件小助手副本做静态提取与反汇编，追踪清理调用链和动效回调，发现其局部路径是串行工作集整理，下降和回弹也有明确的更新顺序。

这些证据用于调整本项目的显示阶段、回弹目标和步进方式，再通过内置浏览器观察本项目真实运行。这里的解包与分析没有得到完整C++源码，静态逻辑也不能直接证明同负载下的速度。它提供的是定位与设计依据，效果仍靠自己的运行证据确认。

# 四、把真实功能和动效拆开，才解决反复不顺的问题
Codex将业务请求和原始结果、后台实时读数、圆环视觉流程分别管理：业务结束立即给结果，动效不能改变报告或追加一次清理，后台读数也不能随意接管正在播放的圆环。

拆分后再校准下降和回弹，才减少了“先被真实读数带着降一次，再播放一次下降”以及回弹终点反复变化的问题。这里值得保留的是先厘清状态和显示权，再调整体验，而不是把某个动画参数直接当作通用答案。

# 五、换Rust与提速，是两件需要分别确认的事
项目按用户要求从Python迁移到Rust，库、CLI和网页共用功能实现，正式程序不再依赖Python。随后Codex补充分段计时，发现既有较慢运行的大部分耗时来自原生工作集调用，不能把迁移语言本身当成已经提速的证明。

这次采用的方法是先拆分耗时，再比较实际处理范围与覆盖。实验候选遇到覆盖不足时保留结果，没有为了得到好看的数字直接切换默认策略。

# 六、对实际发布包再走一次使用流程
开发目录能运行之后，Codex把Windows ZIP解压到含空格的目录，从包内程序启动网页，用内置浏览器完成一次授权的真实整理，再核对记录、停止服务与CMD重新启动。最后比较本地包与GitHub附件的摘要，确认上传的是验收过的产物。

这补上了从“代码能跑”到“别人按说明能用”的一段验证。目前仅支持Windows，后续跨平台也需要分别积累目标环境的运行证据。

# 七、先收集，后归纳
以上保留问题、实际工具和处理方法，暂不变成所有项目必须遵守的要求。其他项目可以继续补充不同经历，再考虑哪些做法具有共同价值。
