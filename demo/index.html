FUTURE WORK · 后续方向

从整理内存，
到提前协调资源。

我们想探索的是：在资源压力持续升高时，根据用户正在做什么，提前协调应用和后台任务。目标是保护任务响应，不是持续压低内存数字。以下均为候选研究，尚未实现自动监测、Linux 接入或 Agent 干预。

WINDOWS

能管理，难在理解业务

Windows 已有内存管理、低内存通知，以及 Job Object 的任务组限额。可以结合应用增长趋势与用户优先级，研究提前预警和受管任务预算。

难点是普通外部工具不知道哪些对象可以删除，也不能通用地拦截所有应用的每次申请。超出硬限额可能导致申请失败，必须核验应用能否处理。

Windows 限额机制 ↗
LINUX

把压力检测与任务组控制连接起来

Linux 的 cgroup v2 可以管理任务组资源，memory.high 用于压力下的节流与回收，memory.max 提供硬限制。PSI 衡量任务因资源不足而停顿的时间，比只看占用百分比更接近受影响程度。

配置适当时，systemd-oomd 可依据压力提前选择任务组终止。但 Linux 也可能换页卡顿，终止可能损失状态，效果仍依赖内核、配置、权限与应用归组。

cgroup v2 ↗PSI ↗systemd-oomd ↗
AGENT

理解优先级，按能力干预

识别持续增长、区分前台任务与重要后台工作，结合用户保护名单解释风险。对有协作接口的应用请求减并发或释放缓存，对自己启动的任务研究预算与延后执行。

AI 用于提出策略，轻量规则执行器负责及时判断、权限、记录和冷却。紧急路径不等待大模型回复，不按内存排名自动杀进程，不承诺防止所有死机。

观察趋势→判断优先级→按授权干预→核对效果

我们准备怎样验证？

  1. 先模拟：用合成轨迹验证持续增长、短时峰值、数据缺失与误判，只输出建议。
  2. 再只读：分别核对 Windows 与 Linux 的数据口径、监测开销和权限，不把当前 Windows 实现当成跨平台支持。
  3. 最后控制：先在可重跑的受管任务上验证预算和应用协作，再评估是否扩大自动动作范围。

比较同样任务在无干预与干预后的响应时间、吞吐、误干预和恢复成本。占用下降或结束一个任务，都不能单独证明方案更好。
